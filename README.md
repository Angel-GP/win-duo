# win-duo

折叠屏「悬浮玻璃」开合动画：

- **实现方式**：用笔记本上盖摄像头 ORB 特征匹配实时测开合角，不依赖额外硬件（独立实现）。
- **动画效果**：来自 [windowsduo](https://github.com/kaedeharakazuha1029/windowsduo)——PyQt6 + GLSL 逆投影「悬浮玻璃」，铰链=屏幕底边，间隙越大越模糊越暗。

效果：**合上笔记本上盖，屏幕内容随开合沉入磨砂玻璃；打开则由虚到实。**
不需要 ESP32、不需要传感器，摄像头的画面就是角度传感器。

新增了一个 windowsduo 原本没有的能力：`outside_mode = "backdrop"`，
让视线出界处用背景图兜底，消掉原本的纯黑场（默认仍是原版的纯黑）。

## 快速开始

```powershell
# 1) 建 venv 装依赖 (工作区内, 不污染系统 Python)
powershell -ExecutionPolicy Bypass -File tools\setup_env.ps1

# 2) 跑 —— 默认进托盘, 玻璃层先不开
.venv\Scripts\python.exe main.py

# 想立刻看到效果 (托盘 + 直接开玻璃层)
.venv\Scripts\python.exe main.py --glass

# 不用摄像头、不用按键, 直接看某个浓度
.venv\Scripts\python.exe main.py --level 0.5
```

或者直接双击启动器（**都用 `pythonw.exe`，不留命令行窗口**）：
`run_camera.bat`（进托盘）/ `run_now.bat`（进托盘 + 强制开玻璃层）/
`run_settings.bat`（进托盘 + 打开设置窗口）。

> 三个启动器行为差别很小：默认配置下玻璃层都会自动开，主要区别是要不要
> 顺带打开设置窗口。

## 屏幕被玻璃层盖住了怎么办

**按 `Ctrl + Alt + Shift + Esc`** —— 立刻关掉玻璃层并退出程序，屏幕恢复正常。

这是系统级热键，不依赖焦点、不依赖托盘、不依赖控制台，任何情况下都有效。

> 为什么需要它：玻璃层是**全屏置顶**窗口。你右键托盘时，托盘菜单会被玻璃层
> 盖住——菜单其实弹出来了、也能点，但你**看不见**，感觉就像"点托盘没反应"。
> 加上托盘模式用 `pythonw` 启动、没有控制台可以按 Esc，屏幕就"回不去了"。
>
> 现在已经顺手修了这个问题：**托盘菜单弹出时会临时收起玻璃层**，所以菜单能
> 正常看见。热键是留给"连托盘都够不到"的情况。

另一个热键：**`Ctrl + Alt + D`** 开关玻璃层（日常用，不用去点托盘）。

两个热键都能在 `config.json` 里改：`hotkey_toggle` / `hotkey_off`，
写成 `ctrl+alt+d` 这种形式（支持 `ctrl`/`alt`/`shift`/`win` + 字母/数字/`F1`-`F24`/
`esc`/`space`/`tab`/`enter`/方向键等）。

## 界面与托盘

**程序启动后只驻留系统托盘，不弹出任何窗口。** 默认 `autostart_glass = true`，
所以玻璃层是**开着**的；但启动时浓度是 0，它会立刻自动隐藏，CPU 落到约 3.6%。
想彻底不启动角度源，就在托盘菜单里关掉玻璃层（那会连摄像头一起停掉 → 0%）。

打开 GUI（设置窗口）只有一种入口 —— **从托盘唤出**，不弹窗：

1. **双击托盘图标**
2. **右键托盘图标 → 设置...**
3. `.venv\Scripts\python.exe main.py --panel` —— 给脚本化/首次配置用

> **最小化**只是把窗口收进托盘，程序继续在后台跑。
> **点 X（关闭）会直接退出整个程序** —— 不是收回托盘。

> 托盘图标在右下角通知区域。Windows 默认会把新图标收进 **`^` 折叠区**，
> 第一次看不到就点一下时钟左边的 `^`，或者把它拖出来固定住。

右键托盘图标：

| 菜单项 | 作用 |
|---|---|
| 开启 / 关闭玻璃层 | 主开关。关闭时会释放摄像头/串口 |
| 设置... | 打开设置窗口（双击托盘图标也可以） |
| 角度源 ▸ | 摄像头 / ESP32 串口 / 键盘手动 |
| 开机自启 | 写 HKCU 的 Run 键，用 `pythonw.exe` 启动，开机不弹控制台 |
| 退出 | 关掉程序 |

设置窗口走 **Fluent Design**（Windows 11 观感，用 `PyQt6-Fluent-Widgets`），
布局刻意做减法——**常用的几行一眼可见，其余收进「▸ 高级设置」，再分成三个标签页**：

```
┌────────────────────────────────────────────┐
│ 悬浮玻璃                          待机  ●──│  ← 总开关
│ 显示器   [NE160QDM-NYJ 1707x1067 缩放 1.5x▾]
│ 浓度     [  0] %                            │  ← 只能键盘输入
│ 角度源              [摄像头│ESP32│键盘]     │  ← 分段选择
│ 摄像头   [index 0 640x480 msmf ▾] [扫描]    │
│          [标定基准帧][翻转方向]              │
│ ▸ 高级设置                                  │  ← 默认收起
│   [效果参数│启动与标定│调试]                │  ← 三个标签页
│     效果参数: 出界处理 / 最大转角 / 眼距 /   │
│               模糊强度 / 重截频率 / 背景图   │
│     启动与标定: 自动标定 / 自动启动 /        │
│               开机自启 / ESP32 串口          │

│ 摄像头 · 追踪中 · pitch 0.00° · 匹配 700    │  ← 实时状态

```

**改动即时生效并自动保存**，没有"保存"按钮、不会忘点丢失。
**最小化**收进托盘（程序继续跑）；**点 X** 直接退出程序。

**日志可以在界面里看**：「高级设置 → 调试 → 查看运行日志...」会弹出实时日志
窗口（启动、角度追踪、设备状态、报错都在里面），还能一键**保存为 `.log` 文件**。
不用再去翻安装目录下的 `win_duo.log`。

没装 `PyQt6-Fluent-Widgets` 也能跑：`ui/widgets.py` 是控件兼容层，会自动退回
普通 Qt 控件 + 一份手写 QSS。想强制走回退路径（测兼容性）就设
`WIN_DUO_NO_FLUENT=1`。两条路径都有测试覆盖。

### 几个刻意的设计决定

- **不出现命令行窗口。** 启动器全部用 `pythonw.exe`，双击 `run_camera.bat`
  后控制台立刻消失（实测 bat 0.89 秒退出，前台 `python.exe` 进程数为 0）。
  输出重定向到 `win_duo.log`。
- **数值一律纯键盘输入，没有滑块也没有上下箭头。** 点进框里打字，**回车或点别处**
  才提交；提交时按范围夹紧并回填规范化的数字（输 `250` 会变成 `100`，输 `007`
  会变成 `7`）。浓度按百分比填（0–100%），其余参数各带自己的单位。
  打字过程中允许中间态（比如范围 30–89 想输 50，第一个字符 `5` 不会被拒）。
- **快捷键只在「键盘」角度源下生效。** 换成摄像头/ESP32 后会自动注销键盘专属
  热键，避免白白吃掉 `Ctrl+Alt+方向键`。`Ctrl+Alt+Shift+Esc` 随时有效。
- **键盘模式用全局热键，不用控制台。** 启动器是 `pythonw`，没有控制台，
  `msvcrt` 读不到按键——所以键盘模式改成了系统级热键，并且在设置窗口里
  列出来。
- **不自动切换角度源。** 摄像头/串口打不开时只弹提示，不会自己跳到键盘模式
  ——模式由你在托盘或设置里显式选择。自动跳走会让人以为程序"自己变了"。
- **摄像头调试窗标题是纯 ASCII 的**（`win-duo match debug`）。OpenCV 的
  HighGUI 在 Windows 上按本地代码页解释窗口标题，写中文会变成乱码。

几个实现上的注意点：

- 换显示器会**同时**改截屏区域（mss 用物理像素，要乘 `devicePixelRatio`）
  和玻璃层窗口几何，两处必须一致，否则采样会错位。
- 关掉玻璃层会**停掉角度源**：摄像头模式常驻要吃约 34% 单核，没必要白占。
  重新开启时会自动重新标定（约 1.5 秒）。
- 摄像头打不开时会自动退回键盘手动模式并弹托盘气泡，不会让你对着一个
  "什么都没发生"的屏幕发呆。

```

config.json                 唯一参数入口
angles/                     角度源层 —— 合并的关键
  base.py                   AngleSource 接口
  camera.py                 上盖摄像头 ORB 测角（独立重写，非移植）
  serial_source.py          ESP32 + MPU6050 串口角度源
  manual.py                 键盘控制, 兼作 manual 角度源
  hub.py                    调度: 注册/启动/轮换, 对外只吐一个 level

  controller.py             AppController: 拥有源/截屏/玻璃层, 管开关与重建
  widgets.py                控件兼容层: Fluent / 普通 Qt 自动切换
  tray.py                   托盘图标与菜单

  net_probe.py              PyPI 连通性探针 (必须用 Python, 不能用 curl)
  offscreen_test.py         离屏验证着色器, 出 PNG + 6 项数值断言
  tracker_test.py           合成帧验证测角算法, 不需要真摄像头
  camera_probe.py           摄像头自检: index×后端 + 冻结帧检测
  camera_track_test.py      真机静止稳定性
  ui_test.py                驱动设置窗口的控件, 验证 GUI 整条链路
  check_smoke.py            分析 --smoke 抓到的帧, 判断折叠是否真的发生
  fov_probe.py              量合成视角下转过多少度后画面还剩多少特征点
  bench_shader.py           着色器真实分辨率性能
```

### 合并的关键：三个角度源归一到 `level ∈ [0,1]`

渲染层只认一个量：

```
level = 0   完全展开, 画面清晰
level = 1   完全合上, 最虚
```

三个源测的本来就是**同一个物理量**（上盖相对底座的夹角），只是传感器不同，
所以可以互换而完全不影响动画：

- `camera` —— 摄像头 ORB 匹配算出上盖俯仰角 `pitch_deg`，再映射
  `fold = clip(180 + SIGN*SCALE*pitch, 0, 180)`、`level = (180-fold)/180`
- `serial` —— 串口角度经 `angle_open/angle_closed` 线性映射
- `manual` —— 键盘直接给

按 `m` 可以运行时轮换，`r` 在「跟随传感器」和「手动覆盖」之间切换。

### 动画内核

windowsduo 的逆投影模型：界面固定在世界空间不动，屏幕是一块玻璃绕底边铰链
转开。每个像素从眼睛出发穿过玻璃像素延长交到界面平面得到采样点；
间隙越大 → 模糊半径越大、越暗。这是**空间效果**：靠铰链处始终清晰，
远端先模糊、先消失。着色器里用 Vogel 盘做磨砂颗粒、mip LOD 分级、
边缘覆盖率平滑。

## 操作

### 键盘模式不占摄像头

**键盘模式下摄像头是完全关着的**——不必要地占着独占设备、还白吃约 34% 单核。
只有在你打开「匹配调试窗」时才会临时打开它，关窗后立刻还回去：

```
[hotkey] ctrl+alt+g             匹配调试窗
[debug] 为调试窗临时打开摄像头 (角度源仍是 manual)
[camera] index=0 用后端 msmf 打开成功
...
[debug] 匹配窗口 关
[camera] 已归还 (当前角度源是 manual)
```

（顺带修了一个真 bug：以前切换角度源只启动新源、**不停旧源**，所以从摄像头
切到键盘后摄像头还在后台跑着。）

### 每种模式的热键不一样

**摄像头模式下只留一个紧急停止键**，别的全不给。摄像头模式是"全自动跟手"的，
多一个键只会误触——尤其浓度键会和自动跟踪打架。标定和翻转方向改用设置窗口
里的按钮。

| 热键 | 键盘模式 | 摄像头模式 |
|---|---|---|
| `Ctrl+Alt+↑` / `↓` 浓度 ±5% | ✅ | — |
| `Ctrl+Alt+→` / `←` 100% / 0% | ✅ | — |
| `Ctrl+Alt+G` 匹配调试窗 | ✅ | — |
| `Ctrl+Alt+D` 开关玻璃层 | ✅ | — |
| **`Ctrl+Alt+Shift+Esc` 紧急关闭** | ✅ | ✅ |
| 合计 | 7 个 | **1 个** |

```
键盘模式: ctrl+alt+d / ctrl+alt+shift+esc / ctrl+alt+g / ctrl+alt+↑↓←→
摄像头模式: ctrl+alt+shift+esc
```

切换角度源时会自动重新注册/注销，设置窗口里显示的**永远只有当前生效的键**。

热键都能在 `config.json` 里改（`hotkey_level_up` 等），写成 `ctrl+alt+d` 这种
形式（支持 `ctrl`/`alt`/`shift`/`win` + 字母/数字/`F1`-`F24`/`esc`/`space`/
`tab`/`enter`/方向键等）。

> 如果某个键注册失败（多半是别的程序占用了，或者同时开了两个 win-duo），
> 设置窗口的列表里**不会显示它**——列表只列真正生效的键。

### 控制台按键（可选）

想用传统的 `↑↓←→` 单键，就用**带控制台**的方式启动：

```powershell
.venv\Scripts\python.exe main.py --source manual
```

这时控制台里的功能键可用（**只在键盘模式下**，`Esc`/`q` 任何时候都能退出）：

| 键 | 作用 |
|---|---|
| `↑`/`w`、`↓`/`s` | 浓度 ±3% |
| `→`/`d`、`←`/`a` | 拉满 100% / 清零 |
| `m` | 轮换角度源 camera → serial → manual |
| `c` | 标定摄像头基准帧（上盖**完全展开**时按） |
| `+`/`-` | camera_scale ±0.1 |
| `f` | 翻转 camera_sign |
| `v` | 出界处理 纯黑 ↔ 背景兜底 |
| `x` | 开关特征匹配调试窗口 |
| `b` | 选背景图（`n` 从配置路径重新加载） |
| `Esc`/`q` | 退出（**任何模式都有效**） |

用 `pythonw`（双击 `.bat`）启动时这一段是禁用的，日志里会说明。

## 性能与卡顿（重要）

### 内存占用（约 110 MB 起步，可再降到 ~40 MB）

托盘待机实测 **约 110 MB**（Windows 工作集）。构成（逐步实测）：

| 阶段 | 累计 WS | 增量 | 说明 |
|---|---|---|---|
| 解释器 + 依赖 | 24 MB | — | numpy / cv2 / PyQt6 / qfluentwidgets |
| `QApplication` | 37 MB | +13 | |
| `apply_theme()` | 76 MB | **+39** | qfluentwidgets 主题 |
| `AppController` | 111 MB | **+35** | 采集线程 + 角度源 |
| ~~`SettingsPanel`~~ | ~~180 MB~~ | ~~+69~~ | **已改成惰性创建**，不再常驻 |
| GL 窗口（用过后） | +127 MB | | 驱动 ~61 + 全屏交换链 ~49 |

两条优化（都**不影响使用体验**）：

1. **设置窗口惰性创建。** `SettingsPanel` 光"建出来"就占 ~69 MB（一堆
   qfluent 控件 + 布局 + 枚举显示器/摄像头），而托盘用户绝大多数时间根本
   不打开它。现在第一次真正要看时才建。**待机 180 → 110 MB。**
2. **限制 BLAS 线程池。** 本机 32 逻辑核，`import numpy` 会让 OpenBLAS 按核数
   开线程池（实测线程数 4 → 27，**私有内存 +740 MB** 的保留栈）。而这个项目
   只算 3×3 矩阵和几百个特征点，多线程纯属白占。`main.py` 在 import numpy
   **之前**设 `OPENBLAS_NUM_THREADS=1` 等环境变量。**私有内存 1099 → 359 MB。**

> **可选：低内存模式**（设置 → 高级 → 调试，或 `--low-memory`）。
>
> **这个模式下玻璃层"要用才建"** —— 启动不预热，待命（浓度≈0）时**根本不建
> GL 窗口**，所以那 ~120MB 的驱动 DLL 映射压根不会加载；窗口一旦不用就销毁
> 并把工作集裁掉。实测：
>
> ```
> 启动后        67 MB
> 25 秒后        5 MB     ← 从没建过窗口 / 建过也裁掉了
> 稳定          5~7 MB
> ```
>
> 那 ~120MB 是 NVIDIA 驱动 DLL（`nvwgf2umx.dll` / `nvgpucomp64.dll` /
> `nvoglv64.dll`）的**文件映射页**：GL 上下文一加载就驻留，**`hide()` 和销毁
> 窗口都不会释放**，只有裁工作集才挤得出去 —— 所以"不建"比"建了再放"更省。
>
> 合盖时会自动建窗口，实测 **~0.43 秒**显示出来（驱动已加载，比冷启动的
> ~960 ms 快）。**默认关**：这 0.4 秒的开合延迟能感觉到。内存紧张时再开。

**实测对比**（托盘待机，autostart_glass=false）：

| | 工作集 | 私有 | 线程 |
|---|---|---|---|
| 优化前 | 180 MB | 1099 MB | 109 |
| 优化后 | **110 MB** | **359 MB** | **47** |

### CPU 与卡顿

玻璃层画的是**每秒只截 `refresh_hz` 次的桌面快照**，而它是全屏置顶的。
只要它常驻显示，你看到的整个桌面就只有几 FPS —— 打字、拖窗口全是卡顿感。
**这和玻璃效果好不好无关，纯粹是快照刷新率的问题。**

所以浓度 ≈ 0（低于 `idle_hide_below`）时，程序会把玻璃层**整个隐藏**，
让真实桌面直接露出来。实测（2560×1600，RTX 4060 Laptop）：

| 状态 | 单核占用 |
|---|---|
| **托盘待机**（玻璃层关着） | **0%** |
| 空闲，浓度 0，玻璃层已隐藏 | 3.6% |
| 玻璃层显示，键盘手动源 | ~20% |
| 玻璃层显示，摄像头源 | ~55% |

> 上表是**手动关掉玻璃层**时的占用。默认 `autostart_glass = true`，启动后玻璃层
> 是开的 —— 但浓度仍是 0，所以它会立刻隐藏，落在"空闲、3.6%"那一档。
> 想真正回到 0%，在托盘菜单里关掉玻璃层（那会连角度源一起停掉）。

摄像头模式内部大致是：Qt 事件循环 + hub ≈ 0%，摄像头 ORB 跟踪 ≈ 34%，
截屏 ≈ 1%，玻璃层显示 ≈ 20%。所以**关掉玻璃层一定要停掉角度源**，
否则白白占着摄像头和 1/3 个核。

### 重截频率上限：从 37 Hz 抬到显示器刷新率

这是本轮最大的性能改动。**换掉了抓屏后端**：

| 后端 | 单帧耗时 | 实际帧率上限 | 说明 |
|---|---|---|---|
| `mss`（GDI BitBlt） | **27~29 ms** | **~37 Hz** | 每次都把整屏重拷一遍 |
| **`bettercam`（DXGI）** | **1.1~1.8 ms** | **~156 Hz** | 走 GPU 复制 |
| `dxcam`（DXGI，备选） | ~2.4 ms | ~150 Hz | bettercam 的上一代 |

> DXGI 必须用 `output_color="BGRA"`。它原生就是 BGRA，请求 RGBA 会多做一次
> 逐像素换 R/B，单次调用从 **1.1ms 涨到 4.4ms**——而 4ms 直接把采集线程忙住，
> 频率就上不去了。（四种格式的**实际帧率**都差不多，都是被刷新率卡住的；
> 差别在单次成本，而单次成本决定了 worker 有多少时间余量。）

所以设置里「重截频率」的上限就是**显示器刷新率**——一个**固定值**（本机
165 Hz），不随负载浮动。理由很直接：合成器每秒最多产那么多帧，抓得再勤也
拿不到更新的画面。

> 我中途试过"用实测单帧耗时算上限"，结果那个数字随负载在 18~165 之间跳，
> 用户看到一个变来变去的上限只会困惑。**上限就该是稳定的"最高可用频率"。**

`bettercam` 在 `requirements.txt` 里；装不上会自动退回 mss，功能不受影响，
只是实际只跑得到 ~37 Hz（上限照样给 165，填高了不会出错——采集线程忙的时候
会自己跳过）。

#### 但"设了 165"不等于"跑到 165"

上限只是个纸面数字。实际速率还受三个环节限制，我一个个量过：

| 环节 | 修之前 | 修之后 |
|---|---|---|
| **tick 定时器**（写死 16ms） | **62 Hz** | 跟着设置走（165Hz → 6ms） |
| **"内容没变就不推进帧号"** | **1 Hz**（等于冻死） | 已删除，见下节 |
| **kick 往返延迟**（~7ms/次） | ~107 Hz | 连续模式，**~139 Hz** |

**实测**（设定 165 Hz，2560×1600）：

```
tick      167 /s
抓屏       56 /s      ← 被内容过滤时只有 1 /s
重绘       28 /s      (render_fps=30)
DXGI 抓帧耗时 1.8 ms/帧
```

状态行现在会直接打出**真实的**截屏速率（`截屏=56/s`），所以不用猜：

```
[键盘手动] 浓度= 50.0% 手动 重绘=28/s 截屏=56/s 出界=黑 …
```

#### 抓屏不比"要画的帧"更勤（省掉近三成单核）

上表里有个反直觉的地方：**设定 165 Hz，但抓屏只有 56/s**。这不是没跑到，
而是**故意压下来的**。

`refresh_hz` 的上限是显示器刷新率（165），但玻璃层本身被 `render_fps`
（默认 30）限速——**每秒最多重绘 30 次**。抓得比这更勤的帧，在下次重绘之前
就被更新的帧覆盖掉了，**上屏的永远是最后那一帧**，多抓的纯属白抓。

而每抓一帧都不便宜：DXGI 给的缓冲不拥有自己的内存，必须 `.copy()` 一份
2560×1600×4 ≈ **16 MB**（见 `capture._store`）。抓 143/s 就是 **2.3 GB/s**
的纯内存拷贝，全花在**根本不会显示**的帧上。

所以渲染层现在把采集频率压到 `min(refresh_hz, 2 × render_fps)`：

| 抓屏频率 | 单核 CPU（level=0.5 静止） | 重绘 |
|---|---|---|
| 143/s（旧行为） | **85.5%** | 27/s |
| **56/s（现在）** | **56.6%** | 29/s |

**省了约 29 个百分点**，重绘反而略高（相位余量更足）。取 2 倍而不是 1 倍是
为了留相位余量：正好等于 `render_fps` 时，抓屏和 tick 错相位会偶尔抓空，
重绘掉到 ~20/s；2 倍就稳定在 28~30/s。

> `refresh_hz` 仍然照旧驱动 **tick 周期**（`_tick_ms`），所以设得高一点
> 仍能让重绘时机卡得更准——只是**抓屏**不再跟着无谓地加码。

> **`截屏` 是"每秒抓了几次"，不是"画面变了多少次"。** 桌面没动的时候帧号不
> 推进、也就不重绘，那正是我们要的（见「光标不闪了」）。所以静止时看到
> `重绘=0/s` 是正常的；`截屏` 仍然会显示真实抓屏频率。
>
> 顺带一提：如果你把 `refresh_hz` 设得很低（比如 5），重绘自然也就只有几
> 次/秒——**那是按你的设置在工作**，不是卡住了。

### 为什么删掉了"画面静止检测"

曾经为了省 CPU 加过一个"桌面没变就不重绘"的过滤：全图采样 4000 个像素，
平均差超过 `static_tol = 1.5` 才算"变了"。

**这个过滤把整个画面冻死了。** 原因很简单：

| 操作 | 影响的像素 | 摊到 400 万像素上的平均差 |
|---|---|---|
| 打字 / 光标闪 | 几百 | ~0 |
| 小窗口刷新 | 几万 | **0.2 ~ 0.3** |
| 滚动一屏 | 几十万 | ~1.2 |
| 整屏视频 | 全部 | ~5 |

日常操作全部落在 **0.2 ~ 0.3**，永远够不到 1.5 的阈值 —— 于是帧号永不推进、
玻璃层停在第一帧。用户看到的就是"**直接变成静态的了，帧率似乎为 0**"。

现在**没有任何内容过滤**：后端给了帧就推进帧号，按你设的 `refresh_hz`
如实刷新。防空转靠另外两条：

- `render_fps`（默认 30）限制**重绘**节奏；
- 浓度≈0 时整个窗口 `hide()`，那才是真正该停的地方。

### 同一时间只能开一个实例

启动第二个实例会被拦住并提示：

```
[!] 已经有一个 win-duo 在运行了。
[!] 两个实例会叠两层玻璃层、还抢全局热键 —— 请先在托盘右键退出
[!] 那一个 (或任务管理器里结束 pythonw.exe), 再启动这个。
```

**为什么必须拦**：两层全屏置顶的玻璃层叠在一起，你看到的那层可能是**旧实例**
的——它连的是旧代码、旧帧，表现就是"画面静止不动，怎么改配置都没用"。同时
后启动的那个还注册不了全局热键（`RegisterHotKey` 撞车），于是"热键也没反应"。
这两个现象加起来极难自查，所以直接拦住。

**症状自查**：如果改了配置完全没效果、热键也失灵，先去任务管理器看一眼是不是
有**两个** `pythonw.exe`（注意：只开一个实例时也会看到两个 —— 那是 venv 的
`pythonw.exe` 转发器拉起的子进程，正常）。

三条修正的要点：

1. **tick 定时器以前写死 16ms**，每秒最多 tick 62 次——设 137 也只会跑 62。
   现在 `interval = min(16, 1000/max(refresh_hz, render_fps, 60))`。
2. **"主线程 kick → 唤醒线程 → 抓 → 回信"一个来回约 7ms**，这条路最多跑到
   ~107 次/秒。现在玻璃层显示时采集线程**自己按目标频率连续跑**，绕开这个
   往返；玻璃层隐藏或收起时立刻回到等待状态，不白烧 CPU。

> **一个被实测推翻的假设。** 我原本以为"DXGI 只在桌面变了才给帧"。
> 实测**不成立**：165 Hz 的屏上合成器每 6 ms 产一帧，内容一模一样也照给。
> 这曾经让我加了一层"内容比对"，结果把画面整个冻死 —— 见下面
> 「为什么删掉了"画面静止检测"」。

**丢帧的代价也不是白给**：mss 那 29 ms 是实打实的 BitBlt，`refresh_hz=30` 会
吃掉 **89% 的单核**。换了后端之后这部分基本归零。

### 打开玻璃层不卡了

点"开启"曾经会僵住约 1 秒。实测拆开是两个独立原因，都已修掉：

| 原因 | 耗时 | 修法 |
|---|---|---|
| 打开摄像头（逐后端试 + 冻结帧检测）在 Qt 主线程同步做 | ~1 s | 挪到采集线程里异步打开 |
| 第一次 `show()` 要建 GL 上下文 + 编译着色器 | **~680 ms** | 启动时**预热**（见下） |

预热实测数据：

```
第 1 次 start_glass = 676 ms      第 2 次 = 3 ms
```

GL 初始化这一步迟早要花，但不能花在你点按钮的那一刻。所以程序启动后（玻璃层
还关着、第一张截图已就绪）先在后台 `show()` 一帧再立刻收起来——因为浓度是 0，
它画的就是桌面本身，即使被合成器抓到一帧也看不出区别。

预热之后：

```
预热本身 769 ms（启动时）    →    首次开启 start_glass = 2 ms
```

异步带来的副作用是"设备打不开"要过一会儿才知道，所以可用性提示推迟到 2.5 秒
后再查。

### 光标不闪了

合上屏时鼠标光标会闪。有三个叠加原因，都改了：

**1. 显隐只有一个阈值。** 测角有死区，边缘抖动时浓度反复穿越单一阈值，
玻璃层就快速 `show`/`hide`。改成双阈值 + 最短驻留：

| 键 | 默认 | 作用 |
|---|---|---|
| `idle_hide_below` | 0.004 | 低于它才收起 |
| `idle_show_above` | 0.02 | 高于它才显示 |
| `idle_dwell_sec` | 0.35 | 两次显隐至少间隔这么久 |

**2. 死区本身是个硬跳变。** 老代码在浓度刚过死区时，直接把控制量从 `0` 跳到
`0.03`（就是死区值本身），等于人为制造了一个台阶。改成**减掉死区再拉伸**，
边界处两边都是 0，连续：

```
刚过死区时的浓度:   修之前 0.030   →   修之后 0.00013
```

**3. 全屏重绘太密。** 浓度连续变化时原来会以 **52~57 次/秒** 重绘一个
2560×1600 的全屏置顶窗，每次都触发整屏合成——鼠标光标叠在上面就会闪。
加了 `render_fps`（默认 30）：

```
浓度连续变化时的重绘:   52~57/s   →   20~23/s
```

**4. 曾经加过"内容没变就不重绘"，已删除。** 详见下面
「为什么删掉了"画面静止检测"」——那层过滤把日常的小变化全判成"没变"，
帧号永不推进，画面直接冻住。现在没有任何内容比对。


### 打开后"什么都没发生"？

摄像头打不开时浓度恒为 0，画面就等于一个静态桌面 —— 看起来像程序没生效。
现在这种情况会**自动退回键盘手动模式**并打印醒目提示，此时按 `→` 拉满浓度
就能看到动画本身。先跑 `tools/camera_probe.py` 确认摄像头可用性。

## 摄像头模式的用法（重要）

1. 摄像头必须是**上盖自带、会随开合转动**的那颗。外接固定摄像头测不到角度。
2. 让摄像头对着**有纹理的静止场景**（书架、墙、房间），别对着纯白墙或自己。
3. 上盖**完全展开**时按 `c` 标定基准帧（启动 1.5 秒后也会自动标定一次）。
4. 慢慢开合上盖，画面就会跟着折叠。
5. 方向反了按 `f`，幅度不合适用 `+`/`-` 调 `camera_scale`。

## 图标

`win-duo.ico` —— 两块玻璃面板 + 中间铰链（表达"折叠屏"），玻璃蓝紫渐变。

**它被应用到这些地方**（全部走 `ui/widgets.py::make_icon()` 一个入口）：

| 位置 | 靠什么设 |
|---|---|
| 任务栏 / Alt-Tab / 通知气泡 | `QApplication.setWindowIcon()`（在 `apply_theme()` 里） |
| 设置窗口、日志窗口标题栏 | 各自的 `setWindowIcon()` |
| 玻璃层（全屏窗，但任务视图里有条目） | `GlassOverlay.__init__` |
| 托盘图标 | `DuoTray(make_icon(), ...)` |
| 桌面快捷方式 | `tools/make_shortcut.py` 写进 `.lnk` 的 IconLocation |

```powershell
.venv\Scripts\python.exe tools\make_icon.py       # 重新生成 .ico
.venv\Scripts\python.exe tools\make_shortcut.py   # 建桌面快捷方式（带图标）
.venv\Scripts\python.exe tools\icon_test.py       # 验证图标真的生效了
```

几点值得说明：

- **.ico 里塞了 9 档尺寸**（16/20/24/32/40/48/64/128/256）。Windows 在托盘、
  任务栏、资源管理器、Alt-Tab 各取所需，缺档它会自己硬缩 —— 硬缩出来的小
  图标又糊又脏。
- **每档单独重绘，不是把 256 缩下去。** 16px 下细线会糊成一团，所以小尺寸
  主动简化（去高光、加粗铰链）。我第一版就因为没做这件事，16px 下铰链和面板
  糊在一起（实测中列亮度 147 = 左面板 148，等于白画）。
- **`.ico` 缺失会自动退回运行时绘制**（`_draw_icon()`，同款设计），所以少一个
  资源文件也不会崩或者显示空白图标。
- **`.bat` 文件本身没法设图标** —— 那是 Windows 按扩展名给的通用图标，文件
  内容里写什么都改不了。要看到自定义图标只能用快捷方式，所以有
  `make_shortcut.py`。

### 摄像头打不开怎么办

主程序会依次尝试 `dshow → msmf → any` 三个后端，成功必须**同时**满足两条：
真的读到一帧，且**画面真的在变**（有些后端 `isOpened()` 为真但 `read()` 一直
失败；虚拟摄像头则会给冻结帧，见下）。任何一条不满足就换下一个后端。

自检会告诉你实际用的是哪个后端，可以把它固定进 `config.json` 的
`camera_backend` 省去试探；但**建议保留 `auto`** —— 因为下面的虚拟摄像头陷阱
意味着固定后端在某些机器上会选错设备。

| 现象 | 处理 |
|---|---|
| 全部 index × 后端都失败 | 设置 → 隐私和安全性 → 相机 → 打开"让桌面应用访问相机" |
| 打不开且提示被占用 | 关掉微信/钉钉/相机应用/浏览器视频页，它们会独占摄像头 |
| 换台机器/接外置摄像头 | `--camera 1` 换 index，`--camera-backend dshow` 指定后端 |
| 能打开但读不到帧 | 用 `--camera-backend dshow`；少数设备 MSMF 会握手失败 |

### ⚠ 虚拟摄像头陷阱（本机实测踩到）

**index 与物理设备的对应关系随后端而变**，而且系统里的虚拟摄像头
（手机投屏 / "Smart Connect Camera" 之类）常常排在前面并给出**冻结的占位图**。
它能打开、也能读到帧，但画面永远不变 —— 测角算法拿冻结帧会永远返回 0，
表现就是"开合上盖毫无反应"，而单看 `isOpened()` 完全发现不了。

本机实测（同一个 index，换个后端就是另一颗摄像头）：

| index | 后端 | 分辨率 | 相邻帧差异 | ORB | 结论 |
|---|---|---|---|---|---|
| 0 | dshow | 1280×720 | **0.000** | 228 | 冻结（虚拟） |
| 0 | **msmf** | 640×480 | 8.75 | 733 | **真实** |
| 1 | **dshow** | 640×480 | 5.34 | 874 | **真实** |
| 1 | msmf | 1280×720 | 0.000 | 242 | 冻结（虚拟） |

所以 `open_camera` 把"画面真的在变"作为取流成功的**必要条件**：`auto` 模式下
dshow 拿到冻结帧会被拒绝，自动换 msmf 重试。真实传感器即使静止也有噪点
（实测差异 5~9），冻结帧恒为 0，判据非常干净。

`tools/camera_probe.py` 会把每个 index × 后端的分辨率、画面变化量、ORB 特征点
数列成表并给出推荐配置。

## 摄像头模式已验证

摄像头这条链**已经用真实硬件端到端验证过**：

- `--selftest --source camera`：msmf 打开成功 → 自动标定成功 → 追踪中，
  匹配点 677 个，PASS
- `tools/camera_track_test.py`：静止 15 秒，pitch 标准差 **0.006 度**、
  范围 -0.02~+0.01 度，匹配点均值 567 最少 205，level 恒为 0 → 稳定
- 合成帧测角精度 **0.04 度**（`tools/tracker_test.py`）

仍未验证的是**真机动态特性**：快速开合时的卷帘快门、曝光漂移、
自动对焦呼吸对测角的影响。这些需要你实际开合上盖才能看出来。

## CPU 占用

实测（2560×1600 + 摄像头 msmf 640×480）：

| 状态 | 单核占用 |
|---|---|
| 空闲，浓度 0，玻璃层隐藏，无摄像头 | 3.6% |
| 摄像头模式常驻 | **69.6%** |

之所以不是 267%：OpenCV 默认在本机会开到 **32 个线程**，而 ORB 的并行 for 是
**自旋等待**的，多出来的线程纯属空转。按 `opencv_threads`（默认 2）限制后：

| OpenCV 线程数 | 墙钟 | CPU |
|---|---|---|
| 32（OpenCV 默认） | 2.94s | **267%** |
| 2 | 3.01s | **86%** |

耗时只多 2%，省下约 1.8 个核。如果你的机器核多且不在乎耗电，可以调大它。


## 已知限制

- **合成测角测试的有效范围约 35 度。** 相机转过 40 度后画面只剩 3.1% 有内容、
  0 个特征点（`tools/fov_probe.py` 实测）。这是合成测试的有限视场，不是算法缺陷：
  真实场景是连续的三维房间，每帧只走零点几度，靠滑动关键帧把总角度串起来。
- **camera_scale 默认 1.1 时 level 上限约 0.855**，即上盖合到底也不会到「最虚」。
  想要满量程把它调到 **1.29** 左右。
- 摄像头模式有固有平滑滞后（One Euro + 渲染层缓动叠加，约 150–250ms）。
  想更跟手就调大 `camera_min_cutoff`（代价是抖动变多）。
- 屏幕分辨率高时截屏有开销；卡顿就调低 `refresh_hz`。

### 打包后文件放在哪

| 文件 | 位置 | 说明 |
|---|---|---|
| `config.json` | **exe 旁边** | 首次启动自动从内置模板生成 |
| `win_duo.log` | **exe 旁边** | 也可以在界面里「高级设置 → 调试 → 查看运行日志」 |
| 背景图（如果自己换过） | **exe 旁边** | 相对路径按这个目录解析 |

想换台机器用：**把 `win-duo.exe` 和 `config.json` 一起拷过去**就行。

> 如果 exe 放在 `C:\Program Files\` 这类**没有写权限**的目录，程序会自动把
> `config.json` / 日志放到 `%LOCALAPPDATA%\win-duo\`，并在日志里说明。
> 免得出现"改了设置重启就没了"这种查不出原因的情况。

### 打包踩过的坑（都在 `tools/build_exe.py` 里处理了）

1. **`win-duo.ico` 是数据文件，PyInstaller 发现不了。** 必须显式 `--add-data`，
   否则打包后托盘/任务栏图标会退回运行时绘制的简版（少 9 档尺寸）。
2. **`config.json` 不能打进 exe。** 它是用户要改的，必须留在外面；第一次启动
   从内置模板复制一份。
3. **`bettercam` / `dxcam` 是 `__import__` 动态导入的**，静态分析看不到。
   必须 `--hidden-import`，否则打包后 DXGI 抓屏失效、静默退回 mss
   （重截频率上限从 165 Hz 掉到 37 Hz，用户只会觉得"变卡了"）。
4. **路径不能用 `__file__`。** onefile 模式下它指向临时解包目录，每次启动都不一样、
   退出就删。所以有 `paths.py` 统一处理：
   - `data_dir()` —— **可写**数据（config、日志）→ exe 旁边
   - `resource_dir()` —— **只读**资源（图标）→ PyInstaller 的解包目录
   - `writable_data_dir()` —— 探测可写性，不行就退到 `%LOCALAPPDATA%`

## 配置

`config.json` 是唯一参数入口。常用项：

| 键 | 含义 |
|---|---|
| `source` | 默认角度源 `camera` / `serial` / `manual` |
| `autostart_glass` | **启动时自动开启玻璃层**，默认 `true` |
| `autocal_on_glass_open` | **开启玻璃层后自动标定一次基准帧**，默认 `true` |
| `camera_autocal` | 摄像头源启动后自动标定，默认 `true` |
| `hotkey_toggle` / `hotkey_off` | 全局热键，默认 `ctrl+alt+d` / `ctrl+alt+shift+esc` |
| `camera_index` / `camera_backend` | 摄像头序号 / 取流后端（`auto` 会自动跳过冻结帧） |
| `camera_axis` | 铰链轴，`x`（默认，上盖绕屏幕水平中线转）/ `y`（摄像头竖装时用） |
| `opencv_threads` | OpenCV 内部线程上限，默认 2（见「CPU 占用」） |
| `camera_scale` / `camera_sign` | 灵敏度 / 方向 |
| `camera_deadzone` | 摄像头角度死区，默认 0.03 |
| `camera_min_cutoff` / `camera_beta` | One Euro 滤波，调大更跟手但更抖 |
| `angle_open` / `angle_closed` | 串口模式的角度映射端点 |
| `max_tilt_deg` | 玻璃最大转角，**30~89**，越大效果越夸张 |
| `eye_dist_h` | 眼距，**0.5~6**（屏高倍数），越小透视越强 |
| `blur_spread` | 模糊强度，**0~1.5**（0 = 只留几何形变不糊） |
| `darkening` / `max_taps` | 吸光 / 采样数上限 |
| `outside_mode` | `black`（原版纯黑）/ `backdrop`（背景兜底，无黑场） |
| `backdrop_path` | 背景图；不存在则用模糊压暗的桌面兜底 |
| `refresh_hz` | 重截频率上限。**上限 = 显示器刷新率**；实际抓屏被压到 `min(它, 2×render_fps)`（见「抓屏不比要画的帧更勤」） |
| `capture_backend` | `auto` / `dxgi` / `mss`，默认 auto（见「重截频率上限」） |
| `render_fps` | 玻璃层重绘上限，默认 30（0 = 不限；全屏重绘太密会让光标闪） |
| `smoothing` | 渲染层缓动系数 |
| `low_memory_mode` | 低内存模式，默认 `false`。开启后玻璃层**要用才建**（待命时不建 GL 窗口），不用就销毁并裁工作集（5~7MB），合盖自动重建（~0.43 秒）（见「内存占用」） |
| `idle_hide_below` / `idle_show_above` / `idle_dwell_sec` | 玻璃层显隐的三个阈值 |

> 上面只是**常用项**。`config.json` 里还有一些微调键（采样数、锁定期、
> 各热键单独绑定等），都有合理默认值，一般不用改。

> `config.json` 里可能还留着 `refresh_hz_idle`（历史配置项），**现在已经没有
> 任何代码读它了** —— 那是"画面静止就降频"的遗留，那套逻辑已整个删除。

## 环境坑（本机实测）

1. **Windows schannel 拿不到凭证**，一切走 schannel 的 TLS 客户端都失败：
   - `curl.exe` → `curl: (35) schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`
   - `git.exe` → 同样报错，必须加 `-c http.sslBackend=openssl`
   - 所以**诊断 PyPI 连通性不能用 curl**，要用 `tools/net_probe.py`（Python 自带 OpenSSL）。

2. **注册表代理没有协议前缀**（`ProxyServer=127.0.0.1:10808`），Python 3.9 的
   `getproxies_registry()` 会把它当成 **TLS 代理**（`https://127.0.0.1:10808`），
   pip 自带的 urllib3 1.26 在 TLS-in-TLS 隧道上直接崩：
   `ValueError: check_hostname requires server_hostname`。
   `tools/setup_env.ps1` 里显式设置 `HTTP_PROXY=http://...` 覆盖掉它；国内镜像用清华源更快。

3. **本机没有 `pwsh`，只有 Windows PowerShell 5.1。** 脚本要用
   `powershell -ExecutionPolicy Bypass -File xxx.ps1` 调用。
   也正因如此 `setup_env.ps1` 的注释全部写成 ASCII —— PS 5.1 对无 BOM 的
   `.ps1` 按 ANSI 解码，中文会乱码。

4. 装到的是 **opencv-python 5.0.0.93**（大版本 5）。
